# Map: Caminito v0.1

Label: wayfinder:map

## Destination

An architecture spec and milestone plan for **Caminito v0.1**, a Rust/Smithay Wayland compositor that runs a usable MATE session with Marco's look and behaviour. The foundation, the Marco features in v0.1, the Wayland protocols and MATE integration, the decoration approach and the milestones are all decided, so implementation can start the next day.

## Notes

- **Domain:** the vocabulary is in [CONTEXT.md](../../CONTEXT.md). Caminito is a *compositor*, never a "window manager".
- **Skills:** every grilling session calls `grilling` and `domain-modeling`, and updates CONTEXT.md and `docs/adr/` inline.
- **Plan, don't do:** tickets produce decisions, not code. A prototype ticket may produce throwaway code as an asset.
- **Tracker:** local markdown. Tickets are in `issues/`, blocking is the `Blocked by:` line, and research findings go on `research/<name>` branches.
- **Settled while charting** (these are fixed; don't reopen them in tickets):
  - Rust on Smithay: [ADR 0001](../../docs/adr/0001-rust-and-smithay.md).
  - XWayland is required in v0.1.
  - Server-side decorations are drawn from Marco/Metacity themes. How much of the theme format is supported was settled by [07](issues/07-decoration-strategy.md).
  - Configuration is read from the existing `org.mate.Marco.*` gsettings, and Wayland-only keys go in a new `org.mate.Caminito` schema.
  - v0.1 session scope: mate-panel (including the window list and workspace switcher applets), mate-session running in the session (who launches whom is for the Session launch model ticket; the MATE Wayland audit shows mate-session can't launch a compositor), mate-settings-daemon, and caja's desktop and background.
  - It ships as its own session entry, "MATE on Caminito", separate from the Wayfire-based MATE Wayland session.
  - Personal project, GPL-2.0-or-later, following MATE conventions where that's cheap.

## Decisions so far

<!-- one line per closed ticket -->

- [Smithay capability audit](issues/03-smithay-capability-audit.md): pin Smithay master; it covers the core, but Caminito writes foreign-toplevel, ext-workspace and output-management plus its own scene graph and window-management policy.
- [Marco feature inventory](issues/01-marco-feature-inventory.md): 194 gsettings keys and 103 keybinding actions; the core behaviour carries over as compositor-internal, and what breaks is Marco's X11 conversations with mate-panel, the pager and mate-control-center.
- [MATE components on Wayland audit](issues/02-mate-wayland-audit.md): MATE needs only wlr/ext protocols (layer-shell, foreign-toplevel, ext-workspace, output-management, data-control), mostly from 2026 git rather than 1.28. mate-session isn't ported and must run as a child of Caminito, and msd leaves input settings and media keys to the compositor.
- [Metacity/Marco theme format](issues/04-metacity-theme-format.md): Marco's format goes up to v3.5 and themes need a lenient parser; colours depend on the GTK3 theme's CSS; feature tiers 0–3 sized from 87 real themes; no non-C renderer exists.
- [v0.1 Marco feature cut](issues/05-v01-marco-feature-cut.md): full Marco parity, meaning every key and action except the X-only and droppable ones; all Marco-to-MATE integrations (Alt+F1/F2, pager layout, shared Show Desktop, both mate-control-center dialogs, window screenshots) are required, via MATE patches carried downstream; Caminito identifies itself as Caminito.
- [v0.1 protocol and integration set](issues/06-v01-protocol-and-integration-set.md): Smithay's protocols plus four built ones (wlr-foreign-toplevel, read-only ext-workspace, wlr-output-management, a minimal gtk_shell1). MATE integration goes through a standard protocol, else an environment variable, else D-Bus on `org.mate.Caminito` ([ADR 0002](../../docs/adr/0002-mate-integration-channels.md)), with carried patches to mate-panel, mcc, msd and mate-screenshot. Caminito owns input settings, idle and the `org.mate.ScreenSaver` shim; msd keeps media keys (grabbing through Caminito) and display persistence.
- [Decoration strategy](issues/07-decoration-strategy.md): Marco's theme engine ported to Rust (cairo/pango, golden-tested against Marco), covering everything Marco draws; GTK colours come from a `caminito-gtk-palette` GTK3 helper with an on-disk cache ([ADR 0003](../../docs/adr/0003-rust-theme-engine-and-gtk-palette-helper.md)). KDE `default_mode=Server`, and xdg-decoration grants the client's choice: MATE, plain GTK and Qt apps are SSD, while header-bar and libadwaita apps stay CSD (GTK can't be forced). CSD windows get no Caminito shadow and shade stays off for them.
- [Session launch model](issues/08-session-launch-model.md): the entry runs `caminito --session`; Caminito starts Xwayland eagerly, exports the environment to D-Bus and systemd, then runs mate-session as its child on XWayland (`GDK_BACKEND=x11`), with a carried patch that unsets `GDK_BACKEND` and drops the `windowmanager` component ([ADR 0004](../../docs/adr/0004-mate-session-as-caminito-child-on-xwayland.md)). `XDG_CURRENT_DESKTOP` stays exactly `MATE`. mate-session exiting ends the session. A carried mate-panel patch sends Shut Down through mate-session.
- [gsettings mapping](issues/09-gsettings-mapping.md): Caminito reads MATE's schemas without owning them. Every key is honoured, never implemented, left to another component, or unsupported (logged once, and only when set away from its default). Input keys go to libinput and xkb exactly as msd applies them on X11. Caminito owns the idle, blank and DPMS keys. A carried msd patch mirrors MATE's appearance settings into the `org.gnome.*` keys that native GTK reads ([ADR 0005](../../docs/adr/0005-msd-mirrors-mate-settings-into-gnome-schemas.md)). `org.mate.Caminito` holds only the three `workspace-layout-*` keys (12 added `locker-command`).
- [XWayland integration audit](issues/10-xwayland-integration-audit.md): Smithay's `X11Wm` covers the per-window ICCCM/EWMH protocol but not desktops, work area, frame extents, struts or the bell, and it exposes no connection, so the recommendation is a second, Caminito-owned X connection that never writes Smithay's properties. Smithay's XSETTINGS claim evicts msd's, so Caminito should serve XSETTINGS itself. An Xwayland crash ends the session, because mate-session is an X11 client. X11 scaling is one global number (goes to 13), and override-redirect windows get their own scene layer.
- [XWayland integration](issues/11-xwayland-integration.md): two X connections, with Caminito's never writing what Smithay maintains, and all X work Caminito-side (upstream PRs optional). Caminito serves XSETTINGS and msd's xsettings plugin runs mirror-only ([ADR 0006](../../docs/adr/0006-caminito-serves-xsettings.md)). v0.1 publishes the desktop atoms, work area and frame extents before `DISPLAY` is exported, and handles the dropped root messages. An Xwayland crash logs the user out, but Caminito restarts X on the same display. XWayland windows follow Marco's type, placement and focus rules, with no activation tokens; override-redirect windows sit above toplevels and the top layer but below overlay and the lock; clipboard access is gated on X11 focus. One global X11 scale; its value goes to 13.
- [Screen locking](issues/12-screen-locking.md): Caminito ships `caminito-locker`, mate-screensaver's unlock dialog ported to gtk-session-lock, with its themes, keys and `mate-screensaver` PAM service ([ADR 0007](../../docs/adr/0007-caminito-locker-ported-from-mate-screensaver.md)); the `org.mate.Caminito` key `locker-command` swaps it. Caminito locks first and fails closed: a crashed locker is restarted, and the last resort is `loginctl unlock-session` from a console. The screensaver shim owns `org.mate.ScreenSaver` and `org.freedesktop.ScreenSaver` before mate-session starts, refuses `Unlock`, and holds a logind sleep delay until the lock is on screen.
- [HiDPI and accessibility scope](issues/13-hidpi-and-accessibility-scope.md): fractional scales are in v0.1. Surfaces get their primary output's scale, and frames render at the largest rounded-up scale they overlap, as GTK3 does. The default output scale is KWin's fractional rule (5% steps, snapped to the nearest integer within 0.06), `window-scaling-factor` 1 or 2 forces an integer, Caminito's saved layout wins (83; it was msd's until ADR 0014), and a carried mcc patch gives the Display capplet 5% steps. The X11 scale is the largest integer output scale, with msd's DPI formulas ([ADR 0008](../../docs/adr/0008-fractional-default-scale-integer-x11-scale.md)). Caminito implements `org.freedesktop.a11y.KeyboardMonitor` for Orca and does sticky, slow and bounce keys itself. Mouse keys, the magnifier, Orca mouse review, an accessible Alt+Tab, typing break and an on-screen keyboard at the lock screen are later. Onboard works in the session over uinput.
- [Development and testing loop](issues/14-development-and-testing-loop.md): GitHub with Actions in an Arch container, committing straight to `master`. Tests are layered: window-management policy generic over a `PolicyWindow` trait with proptest invariants, a Caminito-owned headless backend (pixman, virtual outputs at any scale) with a `wayland-client` test client and insta snapshots, an X11 tier with a real Xwayland and `x11rb`, and theme goldens rendered by a libmarco-private C harness and committed ([ADR 0009](../../docs/adr/0009-committed-marco-goldens-from-libmarco-private.md)). Session-level checks go on a manual checklist run before each milestone closes. Nested runs are winit under `dbus-run-session`; real sessions run on a tty as a second user, because every login of one user shares its systemd manager and bus, and Caminito skips its systemd import when systemd isn't on its bus. Smithay is pinned by `rev`, bumped one commit at a time, with a weekly canary against master. Logs go through `tracing` to journald in a session; debug toggles and an `org.mate.Caminito.Debug` state dump support the checklist.
- [Crate and module architecture](issues/15-crate-and-module-architecture.md): a virtual workspace of `caminito` (the compositor, lib plus bin, with protocols, D-Bus, settings, XWayland and scene as modules), `caminito-policy` (`Policy<W: PolicyWindow>`, Smithay geometry only), `caminito-theme` (no Smithay or GTK) and `caminito-test-client`, plus Meson projects for the C helpers and `marco-frame-dump`. niri's shape: `State { backend, caminito }` in one calloop loop, a `Backend` enum, `Mapped` wrapping Smithay's `desktop::Window` for xdg and XWayland windows alike, in-crate integration tests. Everything but zbus and a GSettings GLib thread runs on the main thread, with no render threads. There's no retained scene graph or `desktop::Space`, and every outward view of policy state is refreshed in one pass per loop iteration ([ADR 0010](../../docs/adr/0010-one-compositor-crate-with-protocol-free-policy-and-theme.md)).
- [Packaging](issues/16-packaging.md): Arch PKGBUILDs in the caminito repo, for the developer only but following AUR conventions. `caminito-git` holds the compositor, both helpers and the data files. A top-level Meson project builds the helpers and installs the data, and cargo runs separately. Five `-caminito` packages (mate-session-manager, mate-panel, mate-control-center, mate-settings-daemon, mate-utils) replace stock MATE through `provides` and `conflicts`, starting from Arch's PKGBUILDs at 1.29.x tags or pinned master commits. Their `format-patch` series sit beside each PKGBUILD. Every carried patch is gated on Caminito (`MATE_WM_NAME=Caminito`, or an owner of `org.mate.Caminito`), so X11 MATE and the Wayfire session are unchanged ([ADR 0011](../../docs/adr/0011-patched-mate-packages-replace-stock-and-gate-on-caminito.md)). `caminito-git` depends on the patched packages by their real names. CI builds the packages with `makepkg` and `namcap`, and the baseline moves only on purpose.
- [Milestone slicing](issues/17-milestone-slicing.md): nine milestones, each closed by a runnable scenario, green CI and its checklist items in the closing commit. M1 nested compositor (workspace, CI, headless fixture, policy proptests, `caminito-git`); M2 Marco frames (theme engine, goldens, palette helper, settings); M3 XWayland; M4 on the metal (tty, fractional outputs, output management, input settings); M5 MATE session (`--session`, layer-shell, foreign-toplevel, ext-workspace, three patched packages); M6 MATE integrations (06's table, the other two patched packages); M7 lock, idle and accessibility, after which the developer uses Caminito daily; M8 Marco parity, audited in `docs/parity.md`; M9 Flatpak, added at M5's closing, with the check of a real sandbox moved to it from M5. v0.1 is done when all nine are closed, the full checklist and CI pass, the six packages are installed with X11 MATE unaffected, and two weeks of daily use have passed with every crash, lock failure and data loss fixed; then `v0.1.0` is tagged.

## Out of scope

- Tiling-WM features beyond Marco's own edge snapping.

- Non-Linux platforms.
- Forking or patching GTK.
- Upstreaming Caminito to the MATE project. That would be a separate effort after v0.1.
- Integrating into or replacing the Wayfire-based MATE Wayland session.
